**Design implications — things Anton must decide (DESIGN.md was NOT edited)**

1. **Orders-menu cards (feature 3.4) cost a dependency.** Vanilla's order cards are built by
   generated code; the only clean way to put our numbers *on* a card is a UIExtenderEx prefab
   patch (+ satellite assembly, + AssemblyGuard, + compatibility risk with RTS Camera Command
   System, which Anton runs and which reworks the order UI). **Recommended instead:** a small
   panel of our own, shown while the order menu is open, one "Infantry 72 ± 8" line per
   formation in the cards' order — no dependency, cannot break vanilla. Alternative (cheapest):
   show the squad bars (feature 3.3) whenever the order menu is open, the way vanilla shows
   its formation markers. Option B (UIExtenderEx) only if Anton insists on "inside the card".
2. **Randomized damage also randomizes knockdown / stagger / dismount / shrug-off.** The
   game's own rules decide them, but they read the FINAL damage (ours) — a 75-roll knocks
   down more often than a 25-roll. Crush-through is decided before damage and is unaffected.
   Recommend: accept (it is still "the game's own rule"); reword DESIGN §1 line 3.
3. **Shield hits.** Blocked blows run through the same damage model (damage goes to the
   shield's HP). DESIGN says people and horses → recommend NOT randomizing shield damage.
   Proposed parameter if wanted: `DamageRandomOnShields` (default false).
4. **What else counts as a "hit that lands"**: fall damage — never randomized (not a strike);
   horse-charge bumps — recommend they follow `DamageRandomMelee`; hits on doors / siege
   engines / objects — not randomized (not people or horses).
5. **What counts as a "blow" for endurance**: kicks and shield bashes are separate actions
   (`ActionCodeType.Kick`, `WeaponBash`) — recommend they cost nothing (DESIGN lists swings,
   thrusts, shots, throws). **Couched lance / braced spear** hits have no swing to detect —
   recommend charging one blow when such a hit LANDS. Siege-engine shots (ballista, onager)
   cost nothing (they do not go through `OnAgentShootMissile`).
6. **Exhaustion cliff + instant recovery.** With the delay (2 × 1.5 s) any sliver above 0
   restores full speed; an AI that keeps swinging stays at 0 (intended). Offer an optional
   hysteresis: `ExhaustedRecoverPercent` (default 0 = DESIGN as written; e.g. 10 = speed
   returns only above 10%).
7. **Looked-at NPC needs two new numbers.** Vanilla's focus event only reaches 10 m and is
   off while the order menu is open, so we raycast ourselves. Proposed parameters:
   `TargetBarMaxDistance` (default 30 m) and `TargetBarLingerSeconds` (default 2 s — the bar
   stays briefly after the aim leaves, so it does not flicker).
8. **Squad bars: always, or only with the formation markers?** Vanilla shows its markers
   only while the "show markers" key is held or the order menu is open. Eight always-on
   bars may clutter. Proposed parameter: `FormationBarsAlways` (default true = DESIGN as
   written; false = only when vanilla shows its markers).
9. **Refresh rates are numbers too** (CLAUDE: every number a parameter). Proposed:
   `HudRefreshSeconds` (0.1) for the player/target bars, `FormationStatsRefreshSeconds`
   (0.25) for averages and std. Advanced group in MCM.
10. **Custom battle "party leader".** `CustomBattleCombatant.General` is set only on the
    player's side (`TaleWorlds.MountAndBlade.CustomBattle\…\CustomBattleHelper.cs`), so the
    enemy commander would never get the leader multiplier. Recommend: in custom battle the
    leader is the side's General, or — when none — the side's hero character(s).
11. **"RCM" is not installed.** The Workshop folder has **RBM** (Realistic Battle Mod,
    2859251492) whose posture/stamina bars are the likely style reference; DESIGN §3 says
    "RCM". Ask Anton which he meant. Also: RBM Harmony-patches combat and has its own
    posture + stamina — **playtest with RBM disabled**; running both means two stamina
    systems.
12. **MaxEndurance changed mid-battle**: recommend keep every fighter's current *fraction*
    (60% stays 60%). One-line decision.
13. **HUD outside fights**: the logic runs in every mission, but the bars should appear only
    in `Mission.Mode` Battle / Duel / Tournament / Stealth (and never while
    `BannerlordConfig.HideBattleUI`). No parameter needed — say if Anton wants one.

New parameters proposed above (for DESIGN's table, if accepted): `DamageRandomOnShields`,
`ExhaustedRecoverPercent`, `TargetBarMaxDistance`, `TargetBarLingerSeconds`,
`FormationBarsAlways`, `HudRefreshSeconds`, `FormationStatsRefreshSeconds`.

## A. Damage — where the final damage is computed

**Verified answer**

- All agent hits — melee (`Mission.MeleeHitCallback`), missiles (`MissileHitCallback`),
  area damage (`MissileAreaDamageCallback`), horse charge (`ChargeDamageCallback`), fall
  (`FallDamageCallback`) — go through one private method,
  `Mission.GetAttackCollisionResults` (`TaleWorlds.MountAndBlade\…\Mission.cs` ~6541).
- It first calls `MissionCombatMechanicsHelper.GetAttackCollisionResults`, whose
  `ComputeBlowDamage` applies armor (`StrikeMagnitudeModel.ComputeRawDamage` with
  `CalculateAdjustedArmorForBlow`), bone multiplier, sneak attack and difficulty →
  `attackCollisionData.InflictedDamage` (clamped 0–2000). Shield-blocked hits go through
  `ComputeBlowDamageOnShield` instead.
- Then, only if that damage is > 0:
  `MissionGameModels.Current.AgentApplyDamageModel.CalculateDamage(...)` and the result is
  written back with `MathF.Round(...)`. After that, knockdown/stagger/dismount/shrug-off
  decisions (`MissionCombatMechanicsHelper.Decide*`) read the new `InflictedDamage`.
- `AgentApplyDamageModel.CalculateDamage` (`…ComponentInterfaces\AgentApplyDamageModel.cs`)
  is **non-virtual**: `IsDamageIgnored` → `ApplyDamageAmplifications` → `ApplyDamageScaling`
  → `ApplyDamageReductions` → **`ApplyGeneralDamageModifiers`** → `Max(0, …)`, each called on
  `MissionGameModels.Current.AgentApplyDamageModel` (i.e. on the top model = us).
- **Decoration works in v1.4.8.** `MBGameModel<T>` (`TaleWorlds.Core\MBGameModel.cs`) has
  `protected T BaseModel`; both `CampaignGameStarter.AddModel<T>` and
  `BasicGameStarter.AddModel<T>` call `GetModel<T>()` (last registered) and
  `gameModel.Initialize(previous)`. `MissionGameModels` picks the LAST registered model of
  each type (`GameModelsManager.GetGameModel<T>`).
- Registration order: campaign → `SandBoxSubModule.OnGameStart` adds
  `SandboxAgentApplyDamageModel`; War Sails adds `NavalAgentApplyDamageModel` (itself a
  decorator); custom battle → `CustomGame.InitializeGameModels` adds
  `CustomAgentApplyDamageModel` BEFORE `GameManager.OnGameStart`; naval custom battle →
  `NavalCustomGame` adds `NavalDLCCustomAgentApplyDamageModel`. `MBGameManager.OnGameStart`
  calls every submodule's `OnGameStart(game, starter)` and only then builds
  `MissionGameModels` from `starter.Models`. So one registration in our `OnGameStart` covers
  all three game types.

**Recommended approach**

```csharp
// Module/Models/TraxDamageModel.cs — decorator, NOT a Default*/Sandbox* subclass
public sealed class TraxDamageModel : AgentApplyDamageModel
{
    public override float ApplyGeneralDamageModifiers(in AttackInformation ai, in AttackCollisionData cd, float dmg)
    {
        float d = BaseModel.ApplyGeneralDamageModifiers(in ai, in cd, dmg);
        try
        {
            if (d <= 0f || !cd.IsColliderAgent || ai.IsVictimAgentNull
                || cd.AttackBlockedWithShield || cd.IsFallDamage) return d;
            // cfg read AT USE TIME (hot swap): enabled, percent, melee/ranged, mounts
            // ranged = cd.IsMissile; mount victim = ai.IsVictimAgentMount;
            // horse-charge = cd.IsHorseCharge (treat as melee)
            return DamageRoll.Apply(d, factor);   // Core: d * U[1-p, 1+p], never below 1 if d > 0
        }
        catch (Exception e) { Log.Error("[damage]", e); return d; }   // fail safe = vanilla
    }
    // EVERY other abstract member: => BaseModel.Same(...)  (IsDamageIgnored, ApplyDamage*,
    // DecideMissileWeaponFlags, CalculateShieldDamage, CalculateSailFireDamage, … ~30 members)
}

// SubModule.OnGameStart(Game game, IGameStarter starter):
if (starter.Models.Any(m => m is AgentApplyDamageModel))
    starter.AddModel<AgentApplyDamageModel>(new TraxDamageModel());
```

- The `Models.Any` guard skips game types without a damage model (no null `BaseModel`).
- "Never rounds below 1": the game does `MathF.Round(result)`, so return `Max(1f, d * f)`.
- RNG: use a thread-safe generator (`[ThreadStatic] Random` in Core) — which thread the hit
  callbacks run on is **UNVERIFIED** (engine callbacks).
- The combat log / "report damage" line shows the rolled number (`combatLog.ModifiedDamage`)
  — a free visual check.

**Risks / open points**

- SubModule.xml: `NavalDLC` as `LoadBeforeThis optional="true"` so we wrap the DLC's model
  (TrainingBattles pattern). Functionally either order works (both delegate).
- RBM (installed on Anton's machine) Harmony-patches combat; compatibility **UNVERIFIED**.
- Implication 2 (knockdown etc. follow the rolled damage) and 3/4 (what is excluded).

## B. Detecting a blow — released and landed

**Verified answer**

- **Ranged release**: `Mission.OnAgentShootMissile` (Mission.cs ~4951) is called by the
  engine for every shot/throw, AI and player, and forwards to
  `MissionBehavior.OnAgentShootMissile(shooterAgent, weaponIndex, position, velocity,
  orientation, hasRigidBody, forcedMissileIndex)` for every behavior. Crossbow = fires on
  the shot (the reload is separate). Siege engines use other paths — they never fire it.
  The engine passes `isPrimaryWeaponShot` but behaviors do not get it: a multi-projectile
  weapon could fire the event more than once per release → dedupe per agent (ignore a
  second shot within ~0.1 s).
- **Melee release: no event.** The only engine callbacks are listed in Mission.cs /
  Agent.cs (`MBCallback`); none marks a swing. `Agent.LastMeleeAttackTime` is only updated
  on a registered HIT (`Agent.UpdateLastAttackAndHitTimes`), not a swing. So: poll
  `agent.GetCurrentActionType(1)` (channel 1 = upper body; vanilla reads attacks there, e.g.
  `Agent.HandleDropWeapon`, `HumanAIComponent.IsInImportantCombatAction`) and count the
  rising edge into `Agent.ActionCodeType.ReleaseMelee` (20). Kicks (`Kick` 28) and shield
  bashes (`WeaponBash` 31) are different codes. Alternative signal:
  `GetCurrentActionStage(1) == Agent.ActionStage.AttackRelease`.
- Cost precedent: vanilla itself polls `GetCurrentActionStage(1)` for every agent —
  `CustomBattleAutoBlockModel` (all humans, per call) and `Agent.TickParallel` (per agent per
  frame, multiplayer). Both are native calls (`MBAPI.IMBAgent`).
- **Landed**: `MissionBehavior.OnMeleeHit(attacker, victim, isCanceled, collisionData)`
  fires once per melee collision — flesh, shield block (`collisionData.AttackBlockedWithShield`),
  parry/block/chamber (`CollisionResult` Parried/Blocked/ChamberBlocked) and object hits.
  A swing that passes through several targets fires it several times → dedupe per swing.
  `MissionBehavior.OnMissileHit(attacker, victim, isCanceled, collisionData)` for missiles.
  `OnAgentHit` / `OnRegisterBlow` / `OnScoreHit` fire only for REGISTERED blows (not for
  blocks/parries) — do not use them for "landed incl. shield".
- Couched lance / braced spear: `attacker.IsDoingPassiveAttack` in `OnMeleeHit`
  (Mission.cs ~5367); there is no release action to poll.

**Recommended approach**

- One `EnduranceLogic : MissionLogic`. Per tracked human agent keep `lastActionType`.
  Each mission tick, for each active tracked agent:
  `var t = a.GetCurrentActionType(1); if (t == ReleaseMelee && prev != ReleaseMelee) Charge(a); prev = t;`
  — flat array loop, no allocations.
- `OnAgentShootMissile` → `Charge(shooter)` (with the 0.1 s dedupe).
- `CostOnMiss == false`: charge from `OnMeleeHit` (first hit of a swing only — key on the
  attacker's swing counter) and `OnMissileHit` with a victim agent, instead of the release.
- Couched/braced hits: `OnMeleeHit` with `attacker.IsDoingPassiveAttack` → one blow
  (implication 5).
- If per-frame polling of ~1000 agents shows up in profiling, move the poll into an
  `AgentComponent.OnTickParallel` (runs on worker threads via `TWParallel.For`,
  `Mission.TickAgentsAndTeamsImp`; vanilla reads the action stage there too) writing only
  the component's own fields, and apply consequences on the main thread.

**Risks / open points**

- **UNVERIFIED**: that every mounted swing shows up as `ReleaseMelee` on channel 1, and how
  long the release phase lasts for the fastest weapons (sets how sparse the poll may get).
  Step 5: log per-agent blow counts with `VerboseLogging` and compare with what is seen.
- Held attacks (hold-to-ready) cost only on release — correct per DESIGN.

## C. Slowing attacks to 20%

**Verified answer**

- Driven properties (`TaleWorlds.Core\DrivenProperty.cs`): `SwingSpeedMultiplier` (66),
  `ThrustOrRangedReadySpeedMultiplier` (67 — thrusts, bow draw, throw), `HandlingMultiplier`
  (68), `ReloadSpeed` (69 — crossbow), `BipedalRangedReadySpeedMultiplier` (95),
  `BipedalRangedReloadSpeedMultiplier` (96).
- Computed by `AgentStatCalculateModel.UpdateAgentStats(agent, props)`; sandbox:
  `SandboxAgentStatCalculateModel.SetWeaponSkillEffectsOnAgent` (swing/thrust/reload from
  weapon skill), `SetMountedPenaltiesOnAgent`; custom battle:
  `CustomBattleAgentStatCalculateModel` (`SwingSpeedMultiplier = 0.93 + 0.0007 × skill`,
  thrust = swing). Throwing speed feeds `ThrustOrRangedReadySpeedMultiplier`. The two
  `Bipedal*` values are global managed parameters (`ManagedParametersEnum` 7/8), not skill.
- Recompute path: `Agent.UpdateAgentProperties()` (public) →
  `AgentDrivenProperties.UpdateDrivenProperties(agent)` →
  `MissionGameModels.Current.AgentStatCalculateModel.UpdateAgentStats(agent, this)` → native
  `UpdateDrivenProperties`. The game calls it on weapon wield/usage change, mount,
  dismount, amount change, etc. (Agent.cs — ~15 call sites). So a DECORATOR's change is
  re-applied by every recompute.
- Clamp: managed code only clamps with `Math.Max(0f, …)` (mounted penalties). **UNVERIFIED**
  whether the native side clamps a 0.2 multiplier — must be measured in game (step 5).
- War Sails' `NavalAgentStatCalculateModel.UpdateAgentStats` calls `BaseModel` first and
  then only touches naval stats / `HandlingMultiplier` — no conflict.

**Recommended approach**

```csharp
public sealed class TraxAgentStatModel : AgentStatCalculateModel   // decorator
{
    public override void UpdateAgentStats(Agent agent, AgentDrivenProperties p)
    {
        ForwardAiLevel();                        // see risk below
        BaseModel.UpdateAgentStats(agent, p);
        try
        {
            if (agent.IsHuman && Endurance.IsExhausted(agent))   // live config read
            {
                float f = cfg.ExhaustedAttackSpeedPercent / 100f;
                p.SwingSpeedMultiplier *= f;
                p.ThrustOrRangedReadySpeedMultiplier *= f;
                p.ReloadSpeed *= f;
            }
        }
        catch (Exception e) { Log.Error("[speed]", e); }
    }
    // every other abstract/virtual member => BaseModel.Same(...)
}
```

- Flip: when an agent enters/leaves exhaustion, set its flag and call
  `agent.UpdateAgentProperties()` once (main thread). Only transitions — never per tick.
- Do NOT scale the `Bipedal*` globals unless the step-5 measurement shows bows/crossbows
  are not slowed (their exact engine meaning is **UNVERIFIED**; scaling both could square
  the penalty). Leave `HandlingMultiplier` alone (defence/handling, not attack speed).

**Risks / open points**

- **Tournament quirk**: `TournamentBehavior` calls
  `MissionGameModels.Current.AgentStatCalculateModel.SetAILevelMultiplier(...)` — a
  NON-virtual method writing a private field `_AILevelMultiplier` of the TOP model, while the
  base model's `SetAiRelatedProperties` reads its OWN field. Any decorator (War Sails' too —
  vanilla already has this bug with the DLC) swallows tournament AI scaling. Fix: before
  delegating, read our own `_AILevelMultiplier` (cached reflection / compiled getter) and, if
  changed, call `SetAILevelMultiplier(value)` on every `AgentStatCalculateModel` in
  `MissionGameModels.Current.GetGameModels()`.
- Every other public member must be forwarded, including virtual ones with a base body
  (`GetEffectiveMaxHealth`, `GetEnvironmentSpeedFactor`, `GetEffectiveSkill`,
  `InitializeMissionEquipment*`, …) — otherwise the base class's default silently replaces
  the sandbox logic.

## D. Movement — standing or moving

**Verified answer**

- `Agent.MovementVelocity` (Vec2, local frame, native `GetMovementVelocity`),
  `Agent.GetCurrentVelocity()` (Vec2), `Agent.Velocity` (Vec3, rotated to world),
  `Agent.AverageVelocity` (Vec3). Vanilla precedents: one check treats
  `GetCurrentVelocity().LengthSquared < 0.25f` (0.5 m/s — our default threshold) as still
  (Agent.cs ~3209); `AgentPathNavMeshChecker` treats `MovementVelocity.LengthSquared > 0.01f`
  as moving.
- Rider → `agent.MountAgent` (null on foot).

**Recommended approach**

- `var m = agent.MountAgent ?? agent; bool moving = m.MovementVelocity.LengthSquared > t*t;`
  with `t = MovingSpeedThreshold`. Sample at the regen rate (e.g. every 0.25 s per agent),
  not every frame.
- Regeneration is a pure Core function of (seconds since last blow, dt, moving) → unit-test it.

**Risks / open points**

- **UNVERIFIED** that a rider's own `MovementVelocity` follows the horse — using the mount's
  avoids the question.

## E. Hero and party leader

**Verified answer**

- `Agent.IsHero` → `Character.IsHero`. Campaign: `CharacterObject.IsHero => _heroObject != null`
  (lords, companions, wanderers, the player). Custom battle: `BasicCharacterObject.IsHero`
  reads XML `is_hero`; `Modules\CustomBattle\ModuleData\custombattlecharacters.xml` has 24
  `is_hero="true"` characters (the selectable lords).
- `Agent.Origin` (`IAgentOriginBase`) → `BattleCombatant` (`IBattleCombatant`).
  Campaign origins: `PartyAgentOrigin` / `PartyGroupAgentOrigin` → the fighter's
  `PartyBase`; `SimpleAgentOrigin` (verified in the tournament fight/archery/jousting,
  arena practice/duel, alley-fight and hideout-ambush controllers) → for a hero,
  `HeroObject.PartyBelongedTo.Party`, else null. So a lord in a tournament is still the
  leader of his own party.
- `PartyBase.LeaderHero => MobileParty?.LeaderHero` (null for settlement parties).
- **Careful**: `IBattleCombatant.General` on a `PartyBase` returns the **army** leader when
  the party is in an army — not the party leader.
- Custom battle: `CustomBattleCombatant.General` = player-side general (or the player);
  enemy side: no general set (`CustomBattleHelper` ~228).

**Recommended approach**

- At spawn (`OnAgentBuild`) cache two booleans per agent (never the product — hot swap):
  `isHero = agent.IsHero`;
  `isLeader = Campaign.Current != null
      ? (agent.Origin?.BattleCombatant as PartyBase)?.LeaderHero?.CharacterObject == agent.Character
      : CustomLeaderRule(agent)` (implication 10).
- Cost per blow = `CostPerBlow × (isHero ? HeroCostMultiplier : 1) × (isLeader ? PartyLeaderCostMultiplier : 1)`, read live.
- `PartyBase`/`Campaign` live in `TaleWorlds.CampaignSystem.dll` (game `bin`, always
  present) — safe to reference even in custom battle.

**Risks / open points**

- Garrison lords in a siege (settlement party, no `LeaderHero`) get the hero multiplier
  only — matches "leads his own party".

## F. Mission lifecycle and per-agent state

**Verified answer**

- `MBSubModuleBase.OnMissionBehaviorInitialize(Mission)` runs for EVERY mission, from
  `Mission.AfterStart` (Mission.cs ~3823): `OnBeforeMissionBehaviorInitialize` → existing
  behaviors' `OnBehaviorInitialize` → **`OnMissionBehaviorInitialize`** → all `EarlyStart` →
  all `AfterStart`. A behavior added here gets `OnCreated`, `EarlyStart`, `AfterStart`, ticks
  and events, but NOT `OnBehaviorInitialize`.
- `MissionState.FinishMissionLoading` calls `Handler.OnMissionAfterStarting` (MissionScreen
  registers the MissionViews that exist NOW) **before** `Mission.AfterStart` → a MissionView
  added in `OnMissionBehaviorInitialize` is never registered (no `MissionScreen`, no
  `OnMissionScreenTick`). Views: see §G.
- Agent events: `OnAgentCreated`, `OnAgentBuild(agent, banner)` (equipment + character
  ready — use this), `OnAgentRemoved(affected, affector, state, blow)`, `OnAgentDeleted`,
  `OnAgentMount` / `OnAgentDismount`. Reinforcements fire `OnAgentBuild` too.
- `Agent.Index` comes from the engine (`creationResult.Index`); reuse after removal is
  possible — validate by reference.
- `AgentComponent` (own subclass allowed): `OnTick` (main thread, `Agent.Tick`) and
  `OnTickParallel` (worker threads). `agent.GetComponent<T>()` is a linear scan.
- Mission kind: `Mission.Mode` (`MissionMode`: Battle, Duel, Stealth, Tournament,
  Deployment, Conversation, …), `IsFieldBattle` / `IsSiegeBattle` / `IsSallyOutBattle` /
  `IsNavalBattle`, `SceneName`. `CombatType` is native-set (no managed setter call found).

**Recommended approach**

- `OnMissionBehaviorInitialize`: `if (!GameNetwork.IsMultiplayer) mission.AddMissionBehavior(new EnduranceLogic());`
  in EVERY mission (cheap; it only acts on attacks). The HUD decides visibility by mode
  (implication 13). Also re-read the config file here (hot swap of hand edits, §J).
- State: `EnduranceState[] byIndex` (grown on demand) + a dense `List<EnduranceState>`

**Recommended approach**

```csharp
internal static class McmBridge            // no MCM type outside method bodies
{
    public static void TryRegister(ModConfig live)   // call from OnBeforeInitialModuleScreenSetAsRoot,
    {                                               // retry from OnApplicationTick until true
        if (_done || !AppDomain.CurrentDomain.GetAssemblies().Any(a => a.GetName().Name == "MCMv5")) return;
        try { _done = Build(live); } catch (Exception e) { _done = true; Log.Error("[mcm]", e); }
    }
    [MethodImpl(MethodImplOptions.NoInlining)]
    private static bool Build(ModConfig c)
    {
        var b = MCM.Abstractions.FluentBuilder.BaseSettingsBuilder.Create("TraxCombatEnhancements_v1", "Trax Combat Enhancements");
        if (b == null) return false;                              // MCM not ready yet
        var s = b.SetFormat("none").SetFolderName("TraxCombatEnhancements")
            .CreateGroup("Damage", g => g
                .AddBool("DamageRandomEnabled", "Damage randomness",
                    new MCM.Common.ProxyRef<bool>(() => c.DamageRandomEnabled, v => Config.Set(nameof(c.DamageRandomEnabled), v, "MCM")),
                    p => p.SetOrder(0).SetRequireRestart(false).SetHintText("…")))
            /* … one line per DESIGN parameter … */
            .BuildAsGlobal();
        s.PropertyChanged += (_, e) => { if (e.PropertyName == "SAVE_TRIGGERED") Config.SaveToFile(); };
        s.Register();
        return true;
    }
}
```

- Format `"none"`: MCM never stores a copy, so `config.json` is the only store and there is
  no "MCM file vs config file" drift. **UNVERIFIED** end to end (the format class exists and
  is dispatched by `BaseSettingsContainer.Load/SaveSettings`).
- Presets: the fluent "Default" preset is filled in `DefaultSettingsBuilder.BuildAsGlobal`
  from each ref's CURRENT value (i.e. the player's loaded values, not ours) → call
  `WithoutDefaultPreset()` and add our own `CreatePreset("trax_defaults", "Mod defaults",
  p => p.SetPropertyValue(id, default)…)` with DESIGN's defaults.
- SubModule.xml: `Bannerlord.MBOptionScreen` as `LoadBeforeThis optional="true"`.
- Keep `tools/AssemblyGuard` from the sibling (fail the package if any type's base type,
  interface or field comes from MCMv5).

**Risks / open points**

- MCM opens inside missions: MCM's UI patches the mission options screen

## J. Hot swap (Anton's requirement, 2026-09-27)

**Verified answer — how MCM notifies**

- MCM's UI writes each edit immediately: `SettingsPropertyVM` → `URS.Do(new
  SetValueTypeAction<T>(PropertyReference, value))` → `DoAction` sets `IRef.Value` → our
  `ProxyRef` setter runs at once and the ref raises `PropertyChanged("Value")`.
- **Cancel** → `ModOptionsVM.ExecuteCancelInternal` → `URS.UndoAll()` → the setters run
  again with the ORIGINAL values. **Done** → `SettingsVM.SaveSettings()` →
  `BaseSettingsContainer.SaveSettings` → format `Save` → settings
  `OnPropertyChanged("SAVE_TRIGGERED")` (`FluentGlobalSettingsContainer` derives from
  `BaseSettingsContainer<FluentGlobalSettings>`). UI files are in
  `Bannerlord.MBOptionScreen.v1.4.8.dll` (decompiled to scratch for this step):
  `MCM.UI.GUI.ViewModels\ModOptionsVM.cs`, `SettingsVM.cs`, `SettingsPropertyVM.cs`,
  `MCM.UI.Actions\UndoRedoStack.cs`; core: `MCM.Implementation\BaseSettingsContainer.cs`.
- So: setter = live value change (log `[config] X: old → new (source: MCM)`, bump a
  `Config.Version` counter); `SAVE_TRIGGERED` = write the file. A Cancel is just more setter
  calls back to the old values — nothing special.
- All MCM UI calls are on the main thread; our readers on the main thread need no lock
  (primitive fields; worker-thread readers, if any, only read).

**Per feature — what re-applying live takes**

| Parameter(s) | Live? | How |
|---|---|---|
| `DamageRandom*` | live | the model reads config on every hit |
| `EnduranceEnabled` | live | logic checks each tick; turning OFF clears every exhausted flag + `UpdateAgentProperties()` on those agents |
| `CostPerBlow`, `CostOnMiss`, hero/leader multipliers | live | read per blow (flags cached, never the product) |
| `MaxEndurance` | live | rescale current values to keep each fraction (implication 12) |
| `ExhaustedAttackSpeedPercent` | live | on `Config.Version` change: `agent.UpdateAgentProperties()` for every exhausted agent — the decorator re-reads the percent. Verified public API, same path as a weapon switch |
| `RegenDelayBlowTimes`, `BlowTimeSeconds`, `FullRegen*`, `MovingSpeedThreshold` | live | read in the regen step |
| `Show*`, `FormationBarsAlways` | live | each view's `OnMissionScreenTick` creates/destroys its layer (the `MissionBattleUIBaseView` pattern); views always exist |
| `FormationSpreadStdDevs`, `FormationBarHeight`, `ShowFormationSpread`, refresh rates | live | read per refresh |
| `VerboseLogging` | live | read per log call |

**Nothing needs "next battle only".** Models are registered once per game start and always
(they are no-ops when disabled), the logic and views are attached to every mission, so every
switch can flip mid-battle. Hand edits of `config.json`: re-read in
`OnMissionBehaviorInitialize` (every mission start) and on game load; diff → `[config] …
(source: file)` lines; bump `Config.Version`.
